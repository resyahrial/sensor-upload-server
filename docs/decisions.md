## API notes (client/grpc)

Verified against grpc-go v1.84.0 source (`server.go`, `internal/transport/handler_server.go`) and protoc-gen-go-grpc 1.6.2 output.

- **Dual registration works (T0).** `grpc.Server.handleStream` strips the leading `/` and splits the path at the *last* `/` into service and method, and `register` stores services in a map keyed by `ServiceDesc.ServiceName` without validating the name. A copy of `UploadService_ServiceDesc` with `ServiceName: "grpc/upload.v1.UploadService"` therefore dispatches `/grpc/upload.v1.UploadService/Init` (and the bidi `Upload` stream) to the same impl. Proven by `internal/grpcprefix` tests (native TCP listener serves bare and prefixed clients; an un-prefixed server answers the prefixed path with `Unimplemented`). The `UnknownServiceHandler` fallback is not needed.
- `grpc.Server.ServeHTTP` takes the method from `r.URL.Path`, so `http.StripPrefix("/grpc", grpcServer)` is enough on the TLS TCP listener (needs HTTP/2, POST, `application/grpc*`). Proven by `TestServeHTTPWithStripPrefix` (httptest TLS + HTTP/2).
- `RegisterService` calls `logger.Fatalf` (process exit) on a duplicate name or after `Serve`; `grpcprefix.RegisterWithPrefix` checks `GetServiceInfo()` first and returns an error instead.
- Interceptor caveat for the prefixed registration: unary `UnaryServerInfo.FullMethod` is the generated constant (`/upload.v1.UploadService/Init`) even on the prefixed path, while `StreamServerInfo.FullMethod` and `grpc.Method(ctx)` carry the real wire path (`/grpc/upload.v1.UploadService/Upload`). Server interceptors must not switch on the exact `FullMethod`.
- `GetServiceInfo()` (and server reflection, if ever enabled) lists both names.
- Client prefix: `grpcprefix.DialOptions("/grpc")` uses `WithChainUnaryInterceptor` / `WithChainStreamInterceptor` (same behaviour as the contract's `withPrefix`, but chain-safe with other interceptors).

- buf 1.28.1 (the installed version) only understands config `version: v1`, so the module config lives in `proto/buf.yaml` with a root `buf.work.yaml` (`directories: [proto]`); `buf lint` and `buf generate` work from the repo root. ## Decisions (uploader)

- Client logic lives in `internal/client` (testable); `cmd/uploader` only parses flags and writes the report.
- Outbox: SQLite via `modernc.org/sqlite`, table `outbox` with the contract §5.1 columns plus `size, filename, content_type, captured_at` (fixed at queue time) and `resumes, bytes_sent, bytes_resent, sent_hwm, result` (report counters that survive a kill). WAL + `synchronous=FULL`, one connection.
- Rows are keyed by `sha256` and looked up by absolute path, so a re-run does not re-hash a queued file. A `done` row is reported from its stored counters; a `failed` row is retried from scratch (attempts reset) on a new run.
- `protocol` column stores the flag label (`grpc-native` too); a re-run with a different protocol clears `upload_ref` (uploads cannot move between endpoints).
- Report counters (`attempts`, `resumes`, `bytes_sent_total`, `bytes_resent`) are cumulative across runs of the same outbox; `duration_ms` is wall time of the current run.
- `bytes_resent` = payload bytes sent at offsets below the highest offset previously handed to the network (`sent_hwm`). `sent_hwm` is written to SQLite *before* each chunk is sent, so a chunk in flight at a kill counts as re-sent on resume (may over-count by one chunk; never under-counts).
- The gRPC client keeps at most `-grpc-window` chunks (default 1) sent but unacked; it no longer pipelines without bound (see "Decisions (grpc window)"). tus is request/response per chunk, so its `bytes_resent` after a kill is ≤ one chunk (asserted, including a real SIGKILL test).
- gRPC: every attempt starts with `Init` (idempotent per sha256, returns `committed_offset`, contract §5.4) instead of `Status`; `Status` is called only when `Init` reports `committed_offset == size`, and the file is marked done only if it says `complete`.
- tus: if `HEAD` shows `Upload-Offset == Upload-Length` but no completing `204` was seen, the client POSTs again; `461` then marks it done (only contract signals are trusted).
- 401/403 and UNAUTHENTICATED/PERMISSION_DENIED are permanent failures: the token is a static flag, there is nothing to refresh.
- 409/FAILED_PRECONDITION and 404/410/NOT_FOUND retry immediately (re-sync via HEAD/Init, or create anew) without backoff; they still count as attempts, bounded by `-retries`.
- `-retries N` = N retries after the first attempt (≤ N+1 attempts per file, cumulative across runs).
- Backoff: `rand[0, min(backoff-max, 1s·2^k)]` (full jitter). `k` resets when an attempt advanced the server offset and is not persisted; `next_retry_at` is persisted and honoured after a restart.
- Timeouts: connect and TLS handshake 15 s; per request 60 s per started 256 KiB of chunk (contract §5.2); QUIC handshake idle 15 s, idle 60 s, keep-alive 20 s; gRPC keepalive 30 s / 10 s, `PermitWithoutStream` (contract §5.4).
- `-h3-fallback`: an HTTP/3 request that gets no HTTP response (dial/handshake/reset) counts as a QUIC failure; 3 in a row → outbox `protocol=rest`, `upload_ref` cleared, new upload on `/rest`, CSV `result=fallback`.
- `result` values: `ok`, `duplicate` (461/ALREADY_EXISTS), `fallback`, `failed`, `interrupted` (SIGINT/SIGTERM; resumable). Exit status is non-zero if any file is `failed` or `interrupted`.
- `content_type` comes from the file extension mapped to the FR-1a allow-list (unknown → `application/octet-stream`, which the server rejects); `captured_at` is the file mtime in RFC 3339; `filename` is the base name.
- `-concurrency N` workers take files in priority order (then `next_retry_at`); each worker drives one file to done/failed.
- gRPC `-url` accepts `https://host:port` (scheme stripped) or a raw gRPC target; both `grpc` and `grpc-native` use the `/grpc` prefix interceptor (`grpcprefix.DialOptions`).
- `-token` defaults to `$UPLOADER_TOKEN` so tokens need not appear in process listings; `-v` enables debug logs.

## Decisions (grpc window)

- Problem: the gRPC client streamed chunks without waiting for acks, so after a kill or outage it re-sent everything past the last ack (client `bytes_resent` 34603008 for 100 MiB after `kill -9` through `/grpc`; 1.8–3.3× overhead on `very-poor`). That failed §15 criterion 2 on the client side and skewed the protocol comparison against tus, whose PATCH waits for its response.
- `-grpc-window N` (chunks, default 1): the sender blocks while `sent_offset − last_acked_offset ≥ N × chunk` (chunk after `max_chunk_bytes`). The ack goroutine wakes the sender through a 1-slot channel; the acked offset is `progress.committed`. Bytes past the last ack are therefore ≤ N chunks, and so is `bytes_resent` after a kill or outage (`sent_hwm` is still claimed before each send, so accounting is unchanged).
- Default 1 = stop-and-wait, the same per-chunk round trip as tus. It costs throughput on high-RTT links; that is the trade the experiment measures, and it matches the server default `GRPC_ACK_EVERY_N=1`.
- `-grpc-window` must be ≥ the server's `GRPC_ACK_EVERY_N` (the server acks every N-th chunk and the final one). Below that the window never opens. The client cannot learn N from the contract, so it is documented in the flag help and here rather than validated.
- Stall guard: while blocked on the window, no ack for the ack timeout ends the stream with a transient error naming `-grpc-window` and `GRPC_ACK_EVERY_N`; the normal retry/backoff loop runs. The timeout reuses the per-request timeout (60 s per started 256 KiB of chunk, contract §5.2) rather than a fixed 30 s, so one slow chunk on `very-poor` does not trip it. `Config.GRPCAckTimeout` overrides it (tests only; no flag). A misconfigured window still completes, slowly: the server commits every chunk it received, so each stream advances by one window (seen in e2e `ack4-window1-stalls`).
- The wait for the final `Ack{complete}` after `CloseSend` is not under the stall guard (finalizing can take long); it is bounded by the stream/server as before.
- `-grpc-window < 1` is a flag error; `Config.GRPCWindow ≤ 0` means 1.
- Experiment driver: `deploy/netem/experiment.sh` passes `$UPLOADER_ARGS` through unchanged, so runs use the default window 1 against the default `GRPC_ACK_EVERY_N=1`; no window dimension in the matrix. A different window is set with `UPLOADER_ARGS="… -grpc-window N"` (and the server's `GRPC_ACK_EVERY_N` ≤ N).
- Server, proto and `internal/grpcapi` unchanged.

### tusd v2 (`github.com/tus/tusd/v2/pkg/handler`)
- Construction: `comp := handler.NewStoreComposer(); filestore.New(dir).UseIn(comp); filelocker.New(dir).UseIn(comp); h, err := handler.NewHandler(handler.Config{StoreComposer: comp, BasePath: "/rest/files/", MaxSize: n, ...})`. Mount it as `mux.Handle(base, http.StripPrefix(base, h))`, because tusd takes the ID from `strings.Trim(r.URL.Path, "/")` (`extractIDFromPath`).
- `Config.PreUploadCreateCallback func(handler.HookEvent) (handler.HTTPResponse, handler.FileInfoChanges, error)`: it runs **before** `Core.NewUpload`. `ev.Upload.MetaData` (type `handler.MetaData`, `map[string]string`) is already base64-decoded by `handler.ParseMetadataHeader`, and `ev.Upload.Size` is set. Return `FileInfoChanges{ID: uuidv7}` to set the upload ID; tusd checks it against `^[A-Za-z0-9\-._~%!$'()*+,;=/:@]*$`, and filestore respects it. Verified: Location ended in the custom ID. Headers in the returned `HTTPResponse` are merged into the 201 (verified: a custom `Upload-Expires` header came through).
- Custom status codes: return an error of type `handler.Error`. `sendError` uses `errors.As(err, &handler.Error{})` and writes `err.HTTPResponse` verbatim; any other error type becomes 500 with `err.Error()` in the body, so do not return raw errors (they leak internals). `handler.NewError(code, msg, status)` sets the body to `"<code>: <msg>\n"`. To get the exact body `already exists`, build the struct literal directly: `handler.Error{ErrorCode: "ERR_ALREADY_EXISTS", Message: "already exists", HTTPResponse: handler.HTTPResponse{StatusCode: 461, Body: "already exists"}}`. Verified: 461 with body `already exists`.
- `Config.PreFinishResponseCallback func(handler.HookEvent) (handler.HTTPResponse, error)`: it is called synchronously from `finishUploadIfComplete` after `upload.FinishUpload`, while the upload lock is held, and **before** the response is sent. A `handler.Error` replaces the 204. Verified: the final PATCH returned 460, and the `Upload-Offset` header is dropped in that case.
- **Hazard (must handle in T11):** once the staged offset equals the size, a later `PATCH` with `Upload-Offset == size` returns **204 immediately without calling PreFinishResponseCallback** (unrouted_handler.go, the `info.Offset == info.Size` short-circuit). Verified: 460 on the last chunk, then a retried empty PATCH got 204. The contract client's `Send` returns nil (done) when `HEAD` reports offset == size. So the tus middleware has to finalize (or report the stored failure) on HEAD and PATCH whenever the row is still `uploading` and the staged offset equals the size. This matches the "recovery on HEAD" decision in the plan, and PATCH needs it too.
- Termination: there is no callback after deletion. Options are `Config.PreUploadTerminateCallback func(HookEvent) (HTTPResponse, error)` (synchronous, before `Terminate`, can reject) or `Config.NotifyTerminatedUploads: true` plus a goroutine draining `h.TerminatedUploads` (an **unbuffered** `chan HookEvent`: the DELETE request blocks until someone reads it, so a consumer is mandatory). Recommendation: mark `cancelled` from the tus middleware after tusd writes 204, or use the notify channel with a dedicated consumer goroutine.
- Extensions advertised (`Tus-Extension`) with filestore: `creation,creation-with-upload,termination,concatenation,creation-defer-length`. Set `DisableConcatenation: true`. `creation-defer-length` is driven by `comp.UsesLengthDeferrer`, which is exported on `*handler.StoreComposer` and can be set to `false` after `UseIn`. **tusd v2 does not implement the `expiration` extension at all**: no `Upload-Expires` header, and `expiration` is never advertised (grepped the whole module). The contract requires it, so T9/T10 must (a) add `Upload-Expires` (RFC 7231 date) via the pre-create `HTTPResponse.Header` for POST, and from middleware for PATCH/HEAD, and (b) rewrite `Tus-Extension` on OPTIONS. tusd sets that header itself with `header.Set` just before writing, so a ResponseWriter wrapper is needed that edits headers in `WriteHeader`. Such a wrapper **must implement `Unwrap() http.ResponseWriter`**: tusd calls `http.NewResponseController(w).SetReadDeadline/SetWriteDeadline` for its `NetworkTimeout` (default 60 s).
- `OPTIONS` returns 200 (not 204) with `Tus-Version`, `Tus-Extension`, and `Tus-Max-Size` when `MaxSize > 0`. Verified.
- `Location` is **absolute**: `proto://r.Host + BasePath + id`, with `https` when `r.TLS != nil` (quic-go http3 sets `req.TLS`, so HTTP/3 also gives `https://…/rest-http3/files/{id}`). `RespectForwardedHeaders` is off by default. If `BasePath` is itself an absolute URL, it is used verbatim. The contract client resolves both forms via `res.Location()`. Decision: keep tusd's absolute URL.
- Locking with `filelocker` (`filelocker.New(dir)`: `HolderPollInterval` 5 s, `AcquirerPollInterval` 2 s) and `Config.AcquireLockTimeout` (default 20 s). A second request on a locked upload **does not get 423**. It creates `{id}.stop`; the holder notices within ~5 s, cancels its request, and the first request returns **400 `ERR_UPLOAD_INTERRUPTED`** (bytes read so far are kept). The second request then acquires the lock. Verified: a HEAD during an in-flight PATCH waited ~6 s and got 200 with the partial offset, and PATCH#1 got 400. If the lock is not released within `AcquireLockTimeout`, the result is **500 `ERR_LOCK_TIMEOUT`**. `handler.ErrFileLocked` (423) exists but neither filelocker nor memorylocker returns it. HEAD and DELETE take the lock too. Consequence: requirement §7 says "423 (tusd locker)", but the real behaviour is lock hand-off (400 to the old request). The T11 test should assert hand-off and the README should list the deviation.
- **filelocker stale-lock hazard:** `github.com/tus/lockfile v1.2.0` treats a lock file whose PID is alive as busy, *including the current process's own PID*. In a container the server is always PID 1, and in-process e2e restarts reuse the test PID. So after a crash (SIGKILL) a leftover `{id}.lock` can never be acquired (every request ends in 500 `ERR_LOCK_TIMEOUT`). Mitigation for T9: on startup, before serving, delete `*.lock` and `*.stop` in the lock directory (safe: single server instance owns `STAGING_DIR/tus`). The alternative, `memorylocker.New()`, has the same hand-off semantics, no file state, and is enough for a single instance.
- `filestore` writes with `O_APPEND` and `Close`, **no fsync**. The offset is `stat(bin).Size()`. This is durable across a process crash (page cache) but not an OS crash; record under NFR-1. `upload.GetReader(ctx)` exists on every `handler.Upload` (v2 interface), so the finalizer can read via `comp.Core.GetUpload(ctx, id)` and then `GetReader`.
- `HookEvent.Context` is a delayed-cancel context (`GracefulRequestCompletionTimeout`, default 10 s). Use it for DB and finalizer work inside hooks.
- Graceful shutdown: tusd interrupts in-flight requests with 503 when the request's context is cancelled with cause `handler.ErrServerShutdown`. Wire `http.Server.BaseContext` to a `context.WithCancelCause` context, and call `cancel(handler.ErrServerShutdown)` from `srv.RegisterOnShutdown` (same as tusd's own `cmd/tusd/cli/serve.go`).
- `Config.Logger` is `*golang.org/x/exp/slog.Logger`, which is a **different type** from `log/slog`. Pass `expslog.New(expslog.NewJSONHandler(os.Stderr, &expslog.HandlerOptions{Level: expslog.LevelWarn}))`, because tusd logs every request at Info, including response bodies.
- `NetworkTimeout` (default 60 s) is the per-read body deadline. NFR-4 asks for 120 s per-request read, so set `NetworkTimeout: 120*time.Second` and no `http.Server.ReadTimeout` (it would cut long PATCHes).
- `s3store`: `s3store.New(bucket, *s3.Client)` with defaults `MinPartSize` 5 MiB, `PreferredPartSize` 50 MiB, `MaxPartSize` 5 GiB, `MaxMultipartParts` 10000, `MaxBufferedParts` 20. A PATCH whose data is < `MinPartSize` and not the final chunk is stored as a separate `{id}.part` object. On the next PATCH that object is **downloaded, deleted and prepended** to the new data. With 64–256 KiB chunks, every PATCH therefore re-transfers up to 5 MiB between server and S3 (~20–80× amplification per part) and adds 3 S3 round trips. Keep `TUS_STAGING=file` as the default and document s3 staging as suitable only for chunks ≥ 5 MiB.

## Foundation decisions
- MinIO image: `docker.io/pgsty/minio` pinned by release tag, for both the testcontainers and compose; the upstream images are no longer anonymously pullable.
- Config: an env var set to an empty/blank value counts as unset, so the default applies. This lets compose files template optional values.
- Config: `DEV_MODE=true` lowers the log level to debug ("verbose logs") unless `LOG_LEVEL` is set explicitly.
- Config: `QUIC_KEEPALIVE` must be shorter than `QUIC_IDLE_TIMEOUT`; otherwise keep-alives cannot prevent the idle close.
- Config: S3 mode requires `S3_BUCKET` and `S3_REGION`. Endpoint and keys are optional, so AWS can use its default credential chain.
- Config: all problems are reported together via `errors.Join`, and the process exits 1 with them on stderr.
- `make devcert`: self-signed P-256 cert (SAN localhost, server, 127.0.0.1, ::1) and an ES256 JWT key pair in `certs/`. Keys are chmod 644 so the distroless nonroot user can read the bind mount. Dev only; `certs/` is gitignored.
- Public listener: `ReadHeaderTimeout` 15 s and `IdleTimeout` 120 s, with no `ReadTimeout`/`WriteTimeout` on `http.Server`. A whole-request deadline would cut long tus PATCHes and gRPC streams. The NFR-4 "120 s read" is enforced per read (tusd `NetworkTimeout`; gRPC per-stream idle).
- Every server's request contexts get a configurable cancellation cause on shutdown (`httpx.ServerConfig.ShutdownCause`), so tusd can answer 503 via `handler.ErrServerShutdown`.
- Shutdown order: public listeners first, admin last, within one shared `SHUTDOWN_TIMEOUT`. `/healthz` keeps answering while uploads drain. After the timeout, the remaining connections are force-closed.
- `/readyz` returns JSON with each check's result. Checks run concurrently with a 2 s timeout. (*Superseded*: the body now says only `ok`/`fail` per check; see "Decisions (review fixes: infra)".)
- Readiness checkers implement `httpx.Checker{Ping(ctx) error}`. `*pgxpool.Pool` satisfies it as-is, and the object store's `Ping` will too.
- The Prometheus registry is created in `main` and injected; Go and process collectors are registered alongside the §10 upload metrics. There is no global registry.
- Migrations: goose `Provider` API (`goose.NewProvider(goose.DialectPostgres, stdlib.OpenDBFromPool(pool), migrations.FS)`), applied at startup. There is no goose global state. `migrations/0001_uploads.sql` is §6 verbatim, plus a `Down`.
- DB startup: `db.Open` retries the ping every 1 s for up to 60 s, because Postgres may still be starting even with compose healthchecks. After that the process exits non-zero.
- `/readyz` checks `postgres` and `staging` (a temp file can be created in `STAGING_DIR`), and since M3 also `objstore` (see "Decisions (finalize/objstore)"), all through the same `httpx.Checker` interface.
- Compose: `podman compose` (podman-compose 1.6.0). Host ports 18443/tcp+udp and 19100 can be overridden with `HOST_HTTPS_PORT`/`HOST_METRICS_PORT`. Postgres and MinIO are not exposed on the host. A one-shot `minio-init` job (`mc mb --ignore-existing local/uploads`) creates the bucket. The server runs with `DEV_MODE=true`, `JWT_ALGS=ES256,HS256` and `OBJSTORE=s3` against MinIO.
- Docker image: `golang:1.26-alpine` build stage, then `gcr.io/distroless/static-debian12:nonroot`. `CGO_ENABLED=0` with `-trimpath -ldflags="-s -w"`, giving 16.2 MB (*superseded*: 19.6 MB after the AWS SDK, see "Decisions (finalize/objstore)"; 22–31 MB measured in "Decisions (load)"). `/data` is pre-created with owner 65532 so named volumes are writable by the nonroot user.
- Lint: staticcheck runs via `go run honnef.co/go/tools/cmd/staticcheck@v0.8.2`, because the local binary was built with go1.23 and cannot load go1.26 modules. Both vet and staticcheck also run with `-tags integration`.
- Auth: `jwt.WithValidMethods(JWT_ALGS)` pins the accepted algorithms (so `none`, RS*, and ES384 are rejected). Keys are chosen by algorithm, so an HS256 token signed with the ES256 public key is rejected (alg-confusion test). `exp` is required, the leeway is 120 s, and `nbf` and `iat` are checked when present (`jwt.WithIssuedAt()`).
- Auth: every verification failure wraps `auth.ErrUnauthenticated`, and a device mismatch wraps `auth.ErrPermissionDenied`. The wrapped detail is for logs only; protocol layers send a fixed short message.
- Auth: the `Bearer` scheme is matched case-insensitively (RFC 7235). Gateways vary in how they case it.
- `auth.Sign` lives in the auth package (not only in `cmd/devtoken`), so unit and e2e tests can mint tokens with the same claims layout. `devtoken` defaults to ES256 with `certs/jwt.key` and a 24 h TTL. HS256 takes `-secret` or `$JWT_HMAC_SECRET`.
- Metadata: `filename` length is counted in Unicode characters (runes), up to 255. It must be valid UTF-8 and must not contain control characters (NUL would break Postgres TEXT and log lines), in addition to the FR-1 `/` and `\` ban.
- Metadata: `content_type` must match the allow-list exactly (case-sensitive, no parameters such as `; charset=`), which is the simplest reading of FR-1a.
- Metadata: `captured_at` accepts any RFC 3339 offset, including `Z`. Exactly +24 h is allowed; later is rejected. There is no lower bound (old files from SD cards are normal).
- Metadata: `priority` must be a plain decimal integer (`strconv.Atoi`), so `" 2"` and `"2.0"` are rejected.
- Metadata: validation reports the first failing field as `*meta.FieldError` (message `"<field>: <reason>"`), which wraps `meta.ErrInvalid` (400) or `meta.ErrTooLarge` (413 for size > `MAX_FILE_BYTES`). Size 0 is a 400.
- Metadata: `meta.ParseUploadMetadata` is a strict parser for the raw `Upload-Metadata` header (rejects empty keys, bad base64, duplicates, extra tokens), so the tus middleware can return a 400 naming `Upload-Metadata` before tusd's lenient parser drops bad pairs. Pairs without a value decode to `""`.
- Final key extension: from the FR-1a mapping (`audio/x-wav` → `.wav`, `video/quicktime` → `.mov`, `image/jpeg` → `.jpg`). Content types added via `CONTENT_TYPES` without a mapping get `.bin`.

## Decisions (netem/experiment)

- Shaping is **egress only**, one `tc qdisc replace dev eth0 root netem rate R delay D J loss L` in the uploader container's own network namespace. Uploads are egress-heavy, and the profile delay then adds to the RTT once (measured ping RTT ≈ profile delay ± jitter), which matches the table's figures as typical link RTTs. No ifb/ingress shaping: the server→client direction (ACKs, responses) is unshaped. netem works at the qdisc level, so TCP and UDP/QUIC are shaped alike (no Toxiproxy).
- The container's `eth0` MTU is set to 1500 before shaping: podman networks on macOS use MTU 65520, which made one packet take 8 s at 64 kbit and turned one netem "loss" into a 64 KiB loss. TSO/GSO/GRO are disabled (best effort, `ethtool -K`) for the same reason (netem would see 64 KiB super-packets).
- netem defaults kept: queue `limit 1000` packets, uniform jitter. With `rate` set, netem schedules each packet after the one queued before it (kernel `netem_enqueue`), so jitter should not reorder packets; consistent with the measured TCP goodput near the profile rate (not separately measured). The `sch_netem` module auto-loads on first use (verified on the podman machine kernel 7.0.9 Fedora CoreOS); no host setup needed.
- Link-down = `tc qdisc change ... netem <same params> loss 100%` and back, not `ip link set down`: taking eth0 down in a container deletes its default route, and `up` does not restore it. The qdisc change keeps addresses/routes, drops all egress (so no data or ACKs leave → both directions are dead for TCP/QUIC), and `up` restores the exact profile.
- Outage schedules: weak-4g period 120 s ± 30 s between outage starts, 10 s down; very-poor period 30 s ± 5 s, 5 s down; leo-sat down for good at 600 s (`LINK_OFF_AFTER`, overridable for tests); good-4g none. The schedule's `RANDOM` is seeded with `OUTAGE_SEED` (the driver passes the rep number), so all protocols in the same rep see the same outage timing.
- Profiles are standalone scripts (`profiles/NAME.sh apply|outages|down|up|clear`) that set variables and source `netem-lib.sh`; `run.sh PROFILE -- ARGS` applies, starts `outages` in the background, runs the uploader (or any command whose first word does not start with `-`, used for the shaping checks), forwards SIGTERM/SIGINT so the uploader writes its report, then removes the qdisc.
- Image: Alpine 3.22 + `iproute2 iproute2-tc ethtool bash coreutils iputils`, root (needs `CAP_NET_ADMIN` in its own netns only). The builder copies only `go.mod go.sum cmd internal gen` (no root `.dockerignore`, which this workstream does not own) and builds with `-p 1 GOGC=25`, because compiling `modernc.org/sqlite` was OOM-killed in the 2 GB podman VM.
- Compose override: `uploader-netem` sits in compose profile `netem` (so `up` does not start it), joins the project's default network, mounts `../results:/results` (samples are generated under `results/samples`) and `../certs:/certs:ro`; no `depends_on` because the server service name belongs to `deploy/docker-compose.yml`.
- Driver is a bash script (`deploy/netem/experiment.sh`, bash 3.2-compatible for macOS) using `xargs -P $EXPERIMENT_PARALLEL` and re-invoking itself as `experiment.sh run ID`; one `docker run --rm --cap-add NET_ADMIN --network $NETEM_NETWORK` per run (not `compose run`) so parallel runs get their own container/netns and a predictable name `netem-ID`. `NETEM_NETWORK` defaults to `deploy_default` (compose default network of project `deploy`); override if the main compose project is named differently.
- Run id `PROTO_PROFILE_SIZE_CHUNK_rREP`; sizes/chunks are KiB/MiB (50KB = 51200 B, 64KB = 65536 B). Order is rep-major, so a partial run already covers every cell once.
- Samples: `results/samples/SIZE.bin` = AES-128-CTR keystream with a fixed key (`openssl enc`), generated once. Each run's file is that base with its last 64 bytes replaced by the space-padded run id, so the size is exact and every run has a unique sha256 (no server-side dedup across runs/reps/protocols). The file is named `ID.flac` so the uploader sends `audio/flac` (allow-listed). Each run gets a fresh `work/ID/uploader.db`; the work dir is deleted once the run's CSV is written.
- Per-run CSV `results/runs/ID.csv` = `run_id,profile,rep,exit_code` + the unchanged §11 uploader columns; written to a temp file then renamed, so a CSV exists only for finished runs and the driver skips exactly those on restart.
- Timeout: GNU `timeout -k 60 $RUN_TIMEOUT` (default 7200 s) around the run (`gtimeout`/Homebrew coreutils on macOS). SIGTERM reaches the uploader via the podman/docker client's signal proxy and `run.sh`, so the uploader still writes its report; the driver keeps those counters and sets `result=timeout`. Without a report it writes a row with elapsed `duration_ms`, zero counters and `result=timeout`.
- A run that exits without any report (e.g. bad flags, image problem) leaves no CSV and is retried on the next start; a report with `result=failed` (e.g. 401 from a wrong token, or retries exhausted) is final. Run `make experiment-smoke` first to catch a bad TOKEN/CA before the full matrix.
- Uploader flags per run: `-retries 100000 -backoff-max 30s` (`UPLOADER_ARGS`), so the 2 h timeout, not the retry budget, bounds a run (very-poor has ~120 outages per hour); 30 s max backoff matches the §11 example. TLS: `-ca /certs/ca.pem` when `CA_FILE` is set, else `-insecure`. The token goes in via `UPLOADER_TOKEN` env, not argv.
- Stopping the driver (SIGINT/SIGTERM) stops xargs and every running run (each forwards SIGTERM through `timeout` to the uploader/container) and waits for them; interrupted runs leave no CSV.
- Test hook `UPLOADER_CMD=CMD`: runs CMD on the host with the same uploader flags instead of the netem container (no shaping, no image/network checks); `deploy/netem/testdata/stub-uploader.sh` is a fake uploader for testing resume/timeout/summary without a server.
- `cmd/summarize`: groups by the uploader's `protocol`, `size`, `chunk` and the driver's `profile`. `n` and `success_rate` count all runs; success = `ok`, `duplicate` or `fallback` (file on the server). Median/p95 of duration, attempts, resumes, bytes_resent and overhead (`bytes_sent_total/size`) are over successful runs only (a timeout's duration is just the timeout); cells with no success have empty stat fields. Median = mean of the two middle values for even n; p95 = nearest rank (`ceil(0.95·n)`-th value). Columns are located by header name; any malformed CSV fails the run.
- `make experiment` / `experiment-smoke` build the netem image first (skipped with `UPLOADER_CMD`) and always regenerate `results/summary.csv` afterwards, then exit with the driver's status. Smoke reuses the same run ids/results dir, so its runs count toward the full matrix.
## Decisions (finalize/objstore)

- AWS SDK: `github.com/aws/aws-sdk-go-v2/feature/s3/manager` v1.23.14 marks `Uploader`/`Downloader` **Deprecated** ("superceded by feature/s3/transfermanager", aws-sdk-go-v2 discussion #3306), so S3 uploads use `feature/s3/transfermanager v0.4.17` (`transfermanager.New(client, opts).UploadObject`). Pinned with `service/s3 v1.114.3`, `config v1.33.9`, `credentials v1.20.9`, `aws-sdk-go-v2 v1.47.3`, `smithy-go v1.28.5`; MinIO tests use `testcontainers-go/modules/minio v0.44.0`.
- S3 memory bound (NFR-2): transfermanager buffers the first read up to `MultipartUploadThreshold` and then up to `Concurrency+1` parts from a pool, so part size = threshold = 5 MiB (S3 minimum) and concurrency 2 → ≤ 15 MiB per in-flight Put, independent of file size. Not configurable (no env var in §8). Objects < 5 MiB use a single PutObject.
- `objstore.Store` has a `Delete` method in addition to `Put`/`Stat`/`Ping`: the finalizer needs it to remove the orphan object a losing duplicate may have written (see finalizer decisions).
- Put idempotency: `Stat` first; same size → return nil without reading the source. A different size (only possible after an sha256 collision or external tampering, since puts are atomic) is overwritten.
- Both stores enforce the declared size exactly (`exactReader`): a short or long source fails the Put and leaves no object (local: temp file removed; S3: single PUT rejected or multipart aborted by the transfer manager).
- Key validation (both stores): non-empty, no leading `/`, no `\` or NUL, no empty/`.`/`..` segments. Keys come from `meta.FinalKey`, so this is defence in depth.
- Local Put: temp file `.put-*` in the target dir → fsync → close → rename → fsync of every directory from the target dir up to the root (MkdirAll may have created several levels that need to be durable too).
- S3 `Stat` detects "missing" by HTTP 404 (`HTTPStatusCode()` via `errors.As`), because HeadObject responses have no body and so no typed `NoSuchKey`.
- S3 `Ping` (readiness) is `HeadBucket`; local `Ping` creates and removes a temp file in the root. `/readyz` lists it as `objstore`.
- S3 credentials: static from `S3_ACCESS_KEY`/`S3_SECRET_KEY` when set, otherwise the AWS default chain; `S3_ENDPOINT` → `s3.Options.BaseEndpoint`, `S3_FORCE_PATH_STYLE` → `UsePathStyle`.
- Repo (`db.Repo`): every state-changing query is conditional on `status = 'uploading'`. Zero affected rows are disambiguated with a follow-up `Get`: `ErrNotFound` (no row) vs `ErrNotUploading` (row in another state). `pgx.ErrNoRows` → `ErrNotFound`.
- Repo: `Complete` is a single `UPDATE … RETURNING` (one implicit transaction) that sets `status`, `storage_key`, `completed_at`, `updated_at` and also `committed_bytes = size_bytes` (tus updates `committed_bytes` only at completion). SQLSTATE `23505` is mapped to `ErrDuplicate` only when `ConstraintName = 'uploads_sha256_completed'`; other unique violations (e.g. `(protocol, upload_ref)`) stay wrapped pg errors.
- Repo: `SetStatus` only accepts the failure states (`failed_checksum`, `cancelled`, `expired`); completion goes through `Complete`.
- Repo: `ListStale(ttl)` compares against the **database** clock (`updated_at < now() - ttl`), the same clock that writes `updated_at`; no row limit (single-instance PoC).
- Repo: `ListFullyCommitted` (`uploading` with `committed_bytes = size_bytes`) is for gRPC crash recovery; tus rows reach that state only at completion, so tus recovery stays on HEAD/PATCH (tusd finding).
- Repo: `FindInProgress` returns the most recent matching `uploading` row (`ORDER BY created_at DESC LIMIT 1`).
- `db.Upload.Metadata()` rebuilds `meta.Metadata` from the row, so the finalizer and recovery paths need only `(protocol, upload_ref)`.
- Finalizer `Input` carries only `(Protocol, Ref, Open, Delete)`: metadata (sha256, size, device, captured_at, content_type) is read from the uploads row, the authoritative copy, so crash recovery and the tus "offset == size" path can finalize from the ref alone.
- Finalizer first loads the row and branches on its state: `completed` → delete staging, return the stored key (crash between steps 4 and 5, or a lost response); `failed_checksum` → delete staging, `ErrChecksum`; `cancelled`/`expired` → delete staging, `ErrDuplicate` if the sha256 is completed elsewhere, else `ErrInactive`. So a protocol layer can call `Run` again to learn a finished upload's outcome (tusd short-circuit finding), and metrics are counted only on the transition, never on a re-run.
- Checksum mismatch: `SetStatus(failed_checksum)` **before** deleting staging, so a crash in between never loses the outcome; the staging left behind is deleted by the cleaner's orphan sweep (corrected, see "Decisions (review fixes: cleanup)"). A staged byte count ≠ `size_bytes` is an internal error (no state change): the caller finalized an incomplete upload.
- The staged file is read twice (hash, then upload) instead of tee-ing into the store: the object is never written for a corrupt upload, and nothing has to be deleted on a mismatch. Memory stays O(1) (`io.Copy` into `sha256`).
- Duplicates: `FindCompletedBySHA` is checked **before** Put, so the common case writes no object. On a race (Complete returns `ErrDuplicate`) the loser deletes its own object **only if its key differs from the winner's `storage_key`** (different device or capture date); the same key is the winner's object and is kept. This is safe because no other row can complete with that sha256 while the winner holds it. The orphan delete happens before the row is cancelled, so a crash in between is redone by the next `Run` (which takes the pre-Put path and deletes the same key again).
- Duplicate loser row → `cancelled` (there is no `duplicate` status in §6) and its staging is deleted immediately instead of waiting 7 days for expiry; the metric is `upload_failed_total{reason="duplicate"}`, not `cancelled`.
- If Complete finds the row no longer `uploading` (concurrent run, cancel, expiry), `Run` re-evaluates from the row's new state. An object already written for a since-cancelled/expired upload is left in place (logged), because another upload with the same device and file may be about to complete with the same key; deleting it could lose a completed file.
- Staging deletion failures (steps 1, 5, duplicate) are logged, not returned: the outcome is already committed in the DB, and the cleaner's orphan sweep deletes what is left (nothing re-runs `Run` for a non-`uploading` row unless a client asks).
- Metrics: `upload_completed_total`, `upload_finalize_seconds` (whole `Run`, successful finalizations only) and `upload_duration_seconds` (`completed_at − created_at`) on completion; `upload_failed_total{reason=checksum|duplicate}` on the state transition; `{reason=internal}` on every `Run` that fails with any other error (one per failed attempt, even if a retry later succeeds).
- Log: one slog line per `Run` with `protocol, upload_ref, device_id, method=finalize, bytes, duration_ms, status (completed|failed_checksum|duplicate|inactive|error), error`.
- `Notifier.Completed(ctx, db.Upload)` runs after staging deletion; its error is logged only. `New(..., nil)` uses `NopNotifier`.
- `cmd/server` builds the object store (and `/readyz` checks it); the repo and finalizer are constructed by the protocol handlers' wiring in wave 3. (*Superseded*: all wiring now lives in `internal/app`, see "Decisions (tus/http3)" and "Decisions (wiring)".)
- Dockerfile: the build runs `go build -p 1` with `GOGC=25`, because compiling `aws-sdk-go-v2/service/s3` in parallel was OOM-killed in the 2 GB podman VM. The image is now 19.6 MB (was 16.2 MB before the AWS SDK).

## Decisions (grpc service)

- `internal/grpcapi` depends on two consumer-side interfaces, `Repo` (7 methods, `protocol='grpc'` rows only) and `Finalizer` (`Run(ctx, FinalizeInput) error`), plus the concrete `*staging.Store`, `*auth.Verifier` and `*obs.Metrics`; `cmd/server` adapts `db`/`finalize` with thin wrappers.
- Sentinels live in `grpcapi` (`ErrNotFound`, `ErrChecksumMismatch`, `ErrDuplicate`); adapters wrap the real packages' errors with them (`fmt.Errorf("%w: %w", grpcapi.ErrDuplicate, err)`), so `grpcapi` imports neither `db` nor `finalize`.
- gRPC row id and `upload_ref` are the same UUIDv7, so every `Repo` method takes one id. (*Refined* in "Decisions (grpc wiring/cleanup)": the DB primary key is a separate UUIDv7 that never leaves the adapter.)
- Init inserts the DB row before creating the staging files: a crash in between leaves a row without staging data (Init then ignores it and starts a new upload; the cleaner expires it) instead of unreferenced files nobody cleans up.
- Init resuming an in-progress upload whose staging info is missing starts a new upload, so a client can never loop on `NOT_FOUND` → `Init` → same id.
- Two concurrent Inits for the same new sha+device can create two rows; not prevented (no unique index on in-progress rows), the finalizer's completed-sha unique index still dedups.
- Crash between the last commit and finalize (`committed == size`, row `uploading`): Init re-runs the finalizer and answers `ALREADY_EXISTS` on success (contract: "already done"), `DATA_LOSS`/`ALREADY_EXISTS`/`INTERNAL` on failure; Status re-runs it and answers `complete: true`; a stream's first chunk re-runs it and answers `Ack{size, complete}`. If a stream holds the upload, Init returns the id with `committed_offset == size` and Status reports `complete: false` without finalizing.
- The final chunk is acked once, with `Ack{committed_offset: size, complete: true}` after the finalizer succeeded; no separate "all bytes committed" ack precedes it.
- A finalizer error other than checksum/duplicate → `INTERNAL`; the row stays `uploading` with every byte committed and is retried on the next Init/Status/stream.
- Status on a completed upload returns `{size, size, complete: true}`; `cancelled`, `expired` and `failed_checksum` uploads are `NOT_FOUND` for Status, Cancel and Upload (the client's action is "Init again").
- An Upload stream on a completed upload → `ALREADY_EXISTS` (same signal as Init dedup).
- Empty `upload_id` → `INVALID_ARGUMENT` ("required"); a non-UUID `upload_id` → `NOT_FOUND` (it cannot exist, and it never reaches the filesystem).
- An empty chunk (`len(data) == 0`) → `INVALID_ARGUMENT`; it would commit nothing and the contract client never sends one.
- Single-holder registry (`Service.Acquire`/`Active`) is shared by streams, Cancel and finalize retries. A second stream → `ABORTED`; Cancel during an active stream → `ABORTED`. The expiry cleaner should `Acquire` (not just check `Active`) while expiring, to close the check-then-delete race.
- Stream open: load+authorize, acquire, then reload the row (a previous holder may have advanced it), load staging info, open the `.bin` and truncate it to the DB offset. A `.bin` shorter than the DB offset is `INTERNAL` (acked bytes missing); missing staging files are `NOT_FOUND`.
- Per chunk: `WriteAt` (fsync) → `SaveInfo` (atomic, fsync) → `Repo.UpdateCommitted` → ack. (*Superseded* in "Decisions (grpc flow control)": the info file is no longer rewritten per chunk.) The DB update and the finalizer run with `context.WithoutCancel(streamCtx)`, so bytes already fsynced are recorded even if the client vanishes mid-chunk.
- Ack frequency: every `AckEveryN`-th chunk of the stream, the final chunk always; when the client half-closes (`CloseSend`) before the end, unacked progress is acked once before the stream ends with OK.
- Per-stream idle timeout (default 120 s, from stream open or the last processed chunk) ends the stream with `DEADLINE_EXCEEDED` (contract: transient, "back off, reconnect"); time spent processing a chunk or finalizing does not count.
- `Service.Shutdown()` makes new calls `UNAVAILABLE` (checked in the interceptors) and ends active streams with `UNAVAILABLE` after the chunk in progress; `cmd/server` should call it before stopping the listeners.
- Auth interceptors apply to every method and never look at `FullMethod` (it differs between bare and prefixed registrations). Exactly one `authorization` value is accepted. Failures return a fixed message; the detail is logged.
- Status codes carry short fixed messages; storage/DB errors are logged and returned as `INTERNAL: internal error`.
- Metrics emitted by `grpcapi` (all `protocol="grpc"`): `upload_started_total` (new upload in Init), `upload_resumes_total` (Init/Status at offset > 0, with `resume_count`), `upload_bytes_received_total` and `upload_chunk_bytes` (per committed chunk), `upload_in_progress` (gauge of open streams holding an upload), `grpc_stream_resets_total` (stream ended with an error and not complete), `upload_failed_total{reason="cancelled"}`. `upload_completed_total`, `upload_failed_total{checksum|duplicate}`, `upload_finalize_seconds` and `upload_duration_seconds` belong to the finalizer (`FinalizeInput.CreatedAt` is passed for the latter). No changes to `internal/obs` were needed.
- Logging: one info line per unary call and per stream end with `protocol, method, device_id, upload_ref, offset_before/offset_after, bytes, chunks, duration_ms, status, error`; per-chunk lines are debug only.
- `NewServer` registers the service bare and with `grpcprefix.RegisterWithPrefix(…, "/grpc")` on one `grpc.Server`, used both for the native listener and behind `PrefixHandler`; it returns an error instead of fataling on a duplicate registration.
- `PrefixHandler` routes only HTTP/2 requests with path prefix `/grpc/` and `Content-Type: application/grpc*` to `grpc.Server.ServeHTTP` (via `http.StripPrefix("/grpc")`); everything else, including `/grpcx/…` and non-gRPC content types on `/grpc/…`, goes to `next`. (*Refined* in "Decisions (grpc flow control)": the server behind it is wrapped in `LimitReadAhead`.)
- Expiry is status-based: an `uploading` row past `INCOMPLETE_TTL` stays resumable until the cleaner marks it `expired`.

## Decisions (grpc wiring/cleanup)

- `grpcadapt.Repo`: `grpcapi.Upload.ID` is the row's `upload_ref`; the DB primary key `id` is a separate UUIDv7 generated by `db.Repo.InsertUploading` and never leaves the adapter (grpcapi only uses ID as the reference). This refines the earlier "row id and upload_ref are the same UUIDv7" line: no `db` change was needed to keep identities consistent.
- `grpcadapt.Repo.Insert` ignores `Upload.Status/Committed/CreatedAt`; the database sets them, and `created_at` from the DB (not the service clock) feeds `upload_duration_seconds`.
- `grpcadapt.Repo` wraps both `db.ErrNotFound` and `db.ErrNotUploading` with `grpcapi.ErrNotFound` (`%w: %w`, original kept in the chain) on every method; `CompletedExists` maps `ErrNotFound` to `false`.
- `grpcadapt.Finalizer`: `finalize.ErrInactive` (row cancelled/expired between the service's lookup and the finalizer, e.g. the cleaner won the registry) and an unknown row are wrapped with `grpcapi.ErrNotFound`; `grpcapi.Service.finalize` now maps that to `NOT_FOUND` (was `INTERNAL`), the contract's "Init again" signal. Retrying a finalize on an expired row can never succeed, so `INTERNAL` (transient) was wrong.
- Metric ownership checked: `finalize` alone counts completed / failed{checksum,duplicate,internal} / finalize_seconds / duration_seconds; `grpcapi` counts none of them, so the adapter adds no metrics.
- Cleaner order: delete staging **before** `SetStatus(expired)` (same as gRPC Cancel). A crash in between leaves an `uploading` row without staged data, which the next run lists and expires again (both protocols already answer missing staging data with "upload gone"); the other order would leave staged files behind an `expired` row that no query ever lists again.
- Cleaner re-checks the row under the lock (`Get`: still `uploading` and `updated_at` unchanged since `ListStale`) before deleting anything, so an upload used between the listing and the lock (a tus PATCH that touched it, a stream that completed it) is skipped instead of expired.
- One expire path for both protocols: the tus side is `cleanup.TusStaging{TryLock(ctx, ref) (unlock, ok, err); Delete(ctx, ref) error}` (lock without waiting and **without** asking the holder to release, since tusd's lockers' hand-off would interrupt an in-flight PATCH); gRPC is adapted to the same shape from `GRPCUploads.Acquire` (`*grpcapi.Service`) and `GRPCStaging.Delete` (`*staging.Store`). Chosen over a single `TryExpire` method because the re-check must run while the lock is held.
- `Deps.Tus` is a map keyed by protocol (`rest`, `rest-http3`), so both tus endpoints can share one staging or use two; a stale row of an unwired protocol is reported as an error and left alone.
- `SetStatus` → `db.ErrNotUploading` (finished meanwhile) is tolerated: no metric, info log, not counted. Per-row errors are joined and returned; the remaining rows are still processed; a cancelled ctx stops the run.
- `Run` does one pass immediately at start and then every `CLEANUP_INTERVAL` (so a server restarted more often than the interval still cleans up); errors are logged, never fatal.
- A stale gRPC row with every byte committed (finalize kept failing) is expired like any other: the client has not asked about it for `INCOMPLETE_TTL`, and Init/Status would have retried the finalize.
- `internal/meta/meta_test.go`: gofmt only.

## Decisions (tus/http3)

- Wiring lives in `internal/app` (`app.New` binds listeners, `App.Run` serves), so `cmd/server` and the in-process e2e harness run identical code; `cmd/server` only loads config and handles signals.
- `tusapi.New` returns the tus handler for one base path with `http.StripPrefix` applied; both handlers share one `tusapi.Staging` (filestore + filelocker under `STAGING_DIR/tus`, or s3store with the locker still in `STAGING_DIR/tus`).
- Store composer holds only core, terminater and locker (no concater, length deferrer, content server); additionally `DisableConcatenation`, `DisableDownload` (GET → 405), CORS disabled (devices, not browsers).
- `Tus-Extension` on OPTIONS is rewritten to exactly `creation,termination,expiration` in a ResponseWriter wrapper (`WriteHeader` hook, implements `Unwrap`). tusd still accepts creation-with-upload bodies; they go through the same hooks and are counted.
- `Upload-Expires` (RFC 7231 date) is added to 2xx POST/PATCH/HEAD responses of unfinished uploads: POST/PATCH = now + `INCOMPLETE_TTL`; HEAD = `updated_at` + TTL (now + TTL when the HEAD counted as a resume). Not sent once the upload completed.
- Every successful PATCH that wrote bytes calls `Repo.Touch` (updated_at), so the cleaner's staleness tracks activity; HEAD with offset > 0 calls `IncrResume` (which also bumps updated_at) and `upload_resumes_total`.
- JWT is required on every tus request including OPTIONS (FR-2 "every request"); failure → 401 with body `unauthenticated` (details only in the log).
- `X-HTTP-Method-Override` is deleted before tusd sees the request: tusd would otherwise turn a POST into PATCH/DELETE behind the per-method checks.
- Upload IDs must be canonical UUID strings (`uuid.Parse` + round-trip); anything else is 404 before any DB or filesystem access.
- tus upload ID = UUIDv7 set in pre-create; DB `upload_ref` = that UUID. With s3store tusd appends `+<multipart id>`; the middleware maps the ID to the ref by cutting at `+`.
- Pre-create order: strict `Upload-Metadata` parse → `meta.FromTus` → `Validate` (400/413 naming the field) → device check (403) → dedup (461 `already exists`) → insert row → `upload_started_total`. Sizes above `MAX_FILE_BYTES` are rejected by tusd's own `MaxSize` check first (413, tusd body).
- All hook errors are `handler.Error` values with short fixed bodies (`internal error` for 500); internal causes go to the request log only.
- Middleware states for HEAD/PATCH/DELETE: unknown / other device / other base path / cancelled → 404; expired → 410; failed_checksum → 460 (all three methods).
- Completed uploads: staging is deleted by the finalizer, so tusd cannot answer; the middleware answers like tusd does for a full upload: HEAD 200 with `Upload-Offset = Upload-Length = size`, PATCH with `Upload-Offset == size` → 204 (else 409), DELETE → 404.
- Short-circuit guard: for HEAD/PATCH on an `uploading` row whose staged offset == size, the middleware takes the upload lock (no hand-off callback), runs the finalizer and answers from the outcome (success → completed responses above, ErrChecksum → 460, ErrDuplicate → 461, ErrInactive → 404, other → 500).
- Finalizer runs (pre-finish, guard) use `context.WithoutCancel` + 10 min timeout: a client that disconnects or a lock hand-off during finalization of a large file must not abort it.
- Pre-finish ErrInactive (row cancelled/expired concurrently) → 404.
- Terminate uses `PreUploadTerminateCallback`: row → `cancelled` + `upload_failed_total{cancelled}` before tusd deletes the staging; if the row is no longer `uploading` the DELETE is refused with 404.
- Metrics: request body bytes are counted by a body wrapper (PATCH and POST) into `upload_bytes_received_total` and one `upload_chunk_bytes` observation per request; `upload_in_progress` = PATCH requests currently being served.
- Request log: one `tus request` line per request with the §10 fields; `offset_before` = staged offset at entry (0 for POST, -1 if unknown), `offset_after` = response `Upload-Offset` or offset_before + bytes read (tusd keeps the bytes of an interrupted PATCH). 4xx at Info, 5xx at Error.
- tusd's `x/exp/slog` logger is adapted to our `log/slog` handler with `component=tusd`, Warn and above only (tusd logs every request and response body at Info).
- filelocker poll intervals lowered to holder 1 s / acquirer 250 ms (defaults 5 s / 2 s) so a resuming HEAD gets the lock from a dead PATCH faster.
- Startup: stale `*.lock` / `*.stop` files in the lock dir are removed before serving (single instance owns the dir). Then `tusapi.Recover` finalizes `uploading` rest/rest-http3 rows whose staged offset == size (rows listed via `ListStale(0)`), bounded by 2 min; failures are logged and left to the HEAD/PATCH guard. Not done for s3 staging (the multipart ID is not stored).
- Expiry cleaner adapter (`Staging.ForCleanup()`, one value for both protocols): an in-process use registry per ref; every HEAD/PATCH/DELETE holds it for its duration, `TryLock` succeeds only when no request holds it (never tusd's lock hand-off), and requests arriving while the cleaner holds it wait and then see the `expired` row (410). With s3 staging `Delete` cannot find the multipart upload by ref and is a no-op (needs a bucket lifecycle rule for abandoned multipart uploads).
- ~~The cleaner is not started in `cmd/server` yet~~ (*superseded*): `cleanup.Deps.GRPC` is required, so it was wired together with the gRPC service; it is now built in `app.New` and started by `App.Run` (see "Decisions (wiring)"). `App.TusCleanup()` gives the tus side.
- TCP router (`httpx.NewRouter`): `/rest/files/` → tus, `/rest-http3/*` → 404, `/grpc/` + `Content-Type: application/grpc*` → `RouterConfig.GRPC` with `/grpc` stripped (nil = 404), else 404. Every TCP response carries `Alt-Svc: h3=":<port>"; ma=86400` with the bound TCP port (behind a port mapping, e.g. compose 18443→8443, it shows the container port; informational only).
- HTTP/3 (`httpx.H3Server`): own UDP socket on the TCP listener's actual port (so `:0` works in tests), TLS 1.3, `quic.Config{MaxIdleTimeout, KeepAlivePeriod}`, `IdleTimeout` 120 s; serves only `/rest-http3/files/`. http3.Server has no BaseContext, so a handler wrapper cancels request contexts with `handler.ErrServerShutdown` when shutdown starts (tusd answers 503); then `Shutdown` (GOAWAY, drain until SHUTDOWN_TIMEOUT) and the socket is closed.
- Concurrent PATCH (§7 says 423): tusd hands the lock off; the first PATCH ends with 400 `ERR_UPLOAD_INTERRUPTED` (its bytes are kept) and the second runs against the new offset (409 if stale). Asserted in `TestConcurrentPatch`; README deviation.
- `objstore.NewS3Client` was split out of `NewS3` so tus s3store staging reuses the same client settings.
- `make test-integration` runs at most `INTEGRATION_P=2` packages in parallel (each starts its own containers; 2 GB podman VM).

## Decisions (wiring)

- `RouterConfig.GRPC` gets the bare `*grpc.Server`: `httpx.NewRouter` already matches `/grpc/` + `application/grpc*` and strips `/grpc`; `grpcapi.PrefixHandler` would strip a second time. Proven by `TestGRPCFullUpload/tls-listener-prefix`; a bare path on the TLS listener is 404 → `UNIMPLEMENTED` (`tls-listener-bare-path-not-routed`).
- One `grpc.Server` (with `grpc.Creds(credentials.NewTLS(sameTLSConfig))`) serves both the TLS listener via `ServeHTTP` (credentials ignored there) and the native listener via `Serve`; the native listener accepts the bare and the `/grpc`-prefixed names. `tls.Config.MinVersion` is set to TLS 1.2 on the shared config so the native listener enforces it too.
- Native listener is bound in `app.New` (port conflicts fail at startup) and wrapped as an `httpx.Service` (`Serve` → `grpc.Server.Serve`, `Shutdown` → `GracefulStop`, `Stop` when `SHUTDOWN_TIMEOUT` expires).
- Shutdown order (one `SHUTDOWN_TIMEOUT` for all steps): `httpx.ShutdownHook` runs `svc.Shutdown()` + new `svc.Drain(ctx)` → TLS TCP `http.Server.Shutdown` (stop accepting + drain tus and ServeHTTP gRPC) → native `GracefulStop` → HTTP/3 drain → admin → `grpc.Server.Stop()` (no-op leftovers) → cleaner stop → DB close. "Stop accepting" and "drain" are one call per listener, so tus over TCP drains before the native gRPC stop; gRPC streams are already gone after Drain, so this costs nothing.
- `grpcapi.Service.Drain` (new, polls the registry every 10 ms) exists because `http.Server.Shutdown` cancels every request context at once (`ShutdownCause` for tusd) and `grpc.Server.GracefulStop` closes `ServeHTTP` transports immediately (`serverHandlerTransport.Drain` = `Close`); waiting for streams to end with `UNAVAILABLE` first makes the client's status deterministic on both listeners (`TestGRPCGracefulShutdown`). Committed-but-unacked bytes were already safe (`WithoutCancel` DB update).
- gRPC crash recovery: no eager startup pass. `grpcapi` already finalizes a fully committed `uploading` row lazily on the next Init, Status or stream (the contract client always calls Init on resume); a row nobody asks about is expired by the cleaner after `INCOMPLETE_TTL`. `Repo.ListFullyCommitted` stays unused by the server.
- The cleaner is built in `app.New` (needs the service's registry and `App.TusCleanup()` for both tus protocols) and started by `App.Run` with its own context, cancelled after the listeners have drained; its first pass runs at startup.
- No test-only API for the cleaner: the e2e test starts the server with `CLEANUP_INTERVAL=200ms`, `INCOMPLETE_TTL=1h` and ages rows via SQL (`TestCleanupThroughApp`).
- e2e harness: `GRPC_NATIVE_ADDR=127.0.0.1:0` by default; the bound port is reused on `Restart`/`start` like the TCP port. The e2e DB is shared by all tests of the package, which run sequentially, so a test's short-TTL cleaner cannot expire another test's rows.
- Compose: `GRPC_NATIVE_ADDR=:9090`, published on `${HOST_GRPC_PORT:-19090}`. The default network is now named `${COMPOSE_NETWORK:-deploy_default}` because the netem harness defaults to `NETEM_NETWORK=deploy_default` while the project name `sensor-upload` produced `sensor-upload_default`. `make devcert` already had `localhost`, `server`, `127.0.0.1`, `::1` as SANs.
- Both `-protocol grpc` and `-protocol grpc-native` store `protocol = 'grpc'` in the DB (the protocol column has no native value); only the client report distinguishes them.

## Decisions (review fixes: tus)

- HEAD/PATCH guard race: the middleware reads the staged info before tusd takes the upload lock, so its `offset == size` check can be stale. tusd's HEAD/PATCH answer for an `uploading` row is now buffered (`recorder`, `Unwrap` to the real writer for deadlines); a 2xx whose `Upload-Offset` equals the staged size while this request did not finalize is discarded and the guard's `finishStaged` answers instead (same outcome mapping).
- The post-check compares with the staged `Upload-Length` read before the lock (it never changes); PATCH responses carry no `Upload-Length`.
- The PATCH post-check is reachable: a PATCH with `Upload-Offset == size` (e.g. an empty retry) whose pre-lock read saw fewer bytes hits tusd's short-circuit 204 after a racing final PATCH staged the rest. A normal final PATCH finalizes in pre-finish and is passed through.
- No separate row re-check before `finishStaged`: the finalizer branches on the row itself (`completed` → stored key + staging deleted), so one call covers "still uploading" and "completed meanwhile".
- e2e `TestHeadRacingFailedFinalPatch` reproduces the race through tusd's real lock hand-off (HEAD waits for the lock, `.stop` file seen, then the last byte is sent); filelocker's 1 s holder poll can interrupt the PATCH first, so the test retries that case up to 3 times. The deterministic variant is the unit test `TestStaleInfoGuard` (a store wrapper serving one stale `GetInfo`).
- 5xx bodies: the response writer replaces the body of every 5xx with a fixed one (`internal error`, or `server shutting down` for 503) and fixes `Content-Type`/`Content-Length` before the header is written; HEAD gets no body and no `Content-Length`. tusd's own text (e.g. `open /data/staging/tus/<id>: no space left on device`) is kept, truncated to 256 bytes, as the request log's `error` when no internal cause was recorded. Applied by status, not by error type, so tusd's own handler.Errors (`ERR_LOCK_TIMEOUT`, `ERR_SERVER_SHUTDOWN`) get the same fixed bodies as ours; 4xx bodies are untouched.
- Guard lock timeout → 423 `upload is locked` (§7 "concurrent access"): `finishStaged` maps `handler.ErrLockTimeout` (what filelocker returns when its context ends), `handler.ErrFileLocked` and `context.DeadlineExceeded`. tusd's own lock timeout inside HEAD/PATCH stays tusd's 500 (README deviation 1): its body is not available for HEAD, so it cannot be told apart from other 500s reliably.
- Shutdown: when the request context's cause is `handler.ErrServerShutdown`, the middleware's own failures (use-registry `enter`, `Repo.Get`, staged info read, guard lock, post-finalize `Get`) answer 503 `server shutting down`, as tusd does; checked before the 423 mapping because a cancelled lock wait also ends in `ErrLockTimeout`. Hook paths (pre-create, pre-terminate) are unchanged: tusd's hook context is cancelled only after its graceful delay.
- `lockTimeout` became a package variable so the unit test can shorten it (20 s in production).
- `Upload-Metadata` is capped at 4 KiB raw (`meta.MaxUploadMetadataBytes`, checked first in the strict parser) → 400 `Upload-Metadata: must be at most 4096 bytes`; pre-create runs before tusd's `NewUpload`, so nothing is stored. 4 KiB leaves room for the six contract keys (~400 bytes encoded with a 255-character filename ≈ 1.4 KiB) plus client extras.
- Unknown metadata keys are still accepted and stored by tusd as sent (tus clients add `filetype`/`name`; rejecting them would break stock clients for no gain once the size is bounded). They are not copied to the DB.

## Decisions (review fixes: cleanup)

- A stale `uploading` row whose bytes are all staged is finalized by the cleaner (under the same TryLock/Acquire) instead of expired; it is expired only if the finalizer reports the row inactive (`ErrInactive` / `db.ErrNotFound`). This reverses "a stale gRPC row with every byte committed is expired like any other" in "Decisions (grpc wiring/cleanup)": a verified complete file must not be lost because the client never came back (FR-8 "safe to retry").
- "Fully staged": gRPC = `committed_bytes == size_bytes` **and** the `.bin` is exactly `size_bytes` (committed_bytes is the authoritative ack; bytes on disk beyond the last commit may be a torn write, so finalizing them could wrongly mark the upload `failed_checksum`). tus = staged offset (filestore `.info` + data size) `== size_bytes` (tus never updates `committed_bytes` before completion).
- A finalizer error other than an outcome (object store down, …) leaves the stale row `uploading` and its staging in place, reported as a run error and retried next pass; it is never expired while complete. An error while checking the staged size also blocks expiry (conservative: data over disk space).
- `ErrChecksum` / `ErrDuplicate` from the cleaner's finalize are final outcomes (the finalizer already recorded them and deleted staging); the cleaner neither expires nor counts them.
- Each pass first retries the finalizer for up to 32 `ListFullyCommitted` rows (no longer dead code), so a gRPC upload whose finalize failed transiently is completed within `CLEANUP_INTERVAL` instead of only on the client's next Init/Status or after the TTL. Rows held by a stream are skipped (Acquire fails). An upload is attempted at most once per pass even if it is also stale. tus rows never show up there (committed_bytes 0), so tus is finalized by the HEAD/PATCH guard, startup `Recover`, or the cleaner once stale.
- The cleaner reads tus staging through a new optional `cleanup.TusFiles{Offset, Open}` interface, implemented by a small filestore adapter in `internal/app` (`tusFiles`, wired only for `TUS_STAGING=file`) rather than in `internal/tusapi` (owned by another change); reading is safe because the cleaner holds the tus use registry exclusively, so no request writes the files. With s3store staging `TusFiles` is nil and stale tus rows are expired as before (the multipart ID is not stored).
- `cleanup.Deps.Finalizer` is required (the app passes the shared `*finalize.Finalizer`); `GRPCStaging` gained `Reader` and `Dir` (both already on `*staging.Store`).
- Orphan sweep (last step of every pass): staged files whose row is terminal (`completed`, `failed_checksum`, `cancelled`, `expired`) or missing are deleted, which covers a crash after `Complete`, after `SetStatus(failed_checksum)`, between tus pre-terminate and tusd's terminate, and mid-`SaveInfo` (`.json.tmp-*`). The finalize doc comments claiming "the next Run finishes it" were wrong (nothing re-runs Run for a non-`uploading` row unless a client asks) and were corrected.
- Safety margin: an upload's files are swept only when its **newest** file's mtime is older than `OrphanAge` (default 1 h, not an env var): an Init/POST in flight, whose row may not be visible yet, is never touched, and only old groups cost a DB lookup.
- Files are grouped by ref; only names `{canonical UUID}{suffix}` are considered (gRPC: `.bin`, `.json`, `.json.tmp-*`; tus filestore: ``, `.info`, `.lock`, `.stop`), everything else in the directories is ignored. tus refs are looked up under each tus protocol (`rest`, then `rest-http3`; refs are unique across them).
- Deletion runs under the upload's lock (gRPC `Acquire`, tus `TryLock`; busy → skipped) through the store's own `Delete` (`staging.Store.Delete` / `tusapi.CleanupStaging.Delete`), then the remaining files of the group (temp files, lock files, data without info) are removed by name. `uploading` rows are never swept (expiry owns them).
- The tus sweep runs only with `TUS_STAGING=file` (`cleanup.Config.TusDir`); with s3store the directory holds lock files only and staged data lives in S3 (bucket lifecycle rule, as before).
- New metric `staging_orphans_deleted_total{staging="grpc"|"tus"}` (one per upload swept) plus an info log `orphaned staging deleted` with `protocol, upload_ref, status (or "missing"), files, modified_at`. Labelled by staging area rather than protocol because a missing row has no protocol.
- `grpcapi.Service.Active` remains unused by production code (only the cleanup integration test's `waitReleased` calls it): the cleaner needs `Acquire` (check-and-hold), never `Active` (check-then-act race). Left in place, since `internal/grpcapi` is owned by another change.

## Decisions (grpc flow control)

Fixes for the two gRPC load findings in `docs/acceptance.md` (NFR-2 / NFR-3). Verified against the grpc-go v1.84.0 and Go 1.26 sources in the module cache / GOROOT.

- Root cause (NFR-2, `/grpc` on the TLS listener) confirmed. In `serverHandlerTransport.HandleStreams` a goroutine reads `req.Body` into pooled 16 KiB buffers and queues them in the stream's unbounded `recvBuffer`. Reading the body hands the HTTP/2 window straight back to the client. Evidence: `TestPrefixPathBoundsReadAhead` stalls the commit loop after one chunk, and before the fix the server read 1,061,369 body bytes (the whole 1 MiB file); after the fix it reads ~66 KB. A heap profile of the NFR-3 load showed 475 MB in `mem.(*sizedBufferPool).Get` under `HandleStreams.func2`.
- `grpcapi.LimitReadAhead(h, maxMsg)` wraps the `grpc.Server` on the TLS listener (`internal/app` and `PrefixHandler` callers). It replaces `r.Body` with a reader that blocks while the buffers it has filled, and gRPC has not yet handed to the handler, reach a 64 KiB soft budget. It also stores itself in the request context. Verified: `ServeHTTP` → `serveStreams(r.Context())` → `HandleStreams(ctx)` → stream context, so the value reaches the stats handler.
- Release uses a `stats.Handler` (`readAheadStats`, installed by `NewServer`), not per-handler `Recv` accounting. `InPayload.WireLength` is the exact wire size of each received message (5-byte header plus the possibly compressed payload). Compression therefore cannot make the accounting drift and need not be rejected. `consume` never counts more than has been read.
- Each Read is charged `len(p)` (the 16 KiB buffer grpc-go keeps alive), not the bytes it returned. Charging bytes let 4x the budget pile up with 4 KiB chunks (NFR-3 heap profile: 475 MB). A charged read is released once all its bytes have been consumed (FIFO of reads).
- No deadlock: the reader parses the gRPC framing it passes through. Above the budget a Read is still allowed while no complete message is buffered, so a message of any accepted size always arrives. A message needing more than `4 x (maxMsg + 5) + 64 KiB` of buffers (a client splitting it into very many tiny frames) fails the body instead of growing without bound.
- Unblocking: Reads return on request-context done and on `Close`. grpc-go closes the body when the stream's status is written and waits for its reader before `ServeHTTP` returns. `LimitReadAhead` also stops the reader when the wrapped handler returns.
- First version used a byte budget of 2 x (max_chunk + 64 KiB). It passed NFR-2 at 283 MB but NFR-3 rose to 729 MB because of the per-buffer cost above. The second version charged per buffer with a one-message budget (320 KiB). NFR-3 was then 270–341 MB and RSS followed the GC target (~2x live heap). The soft budget is now 64 KiB (the native stream window), which the framing check makes safe.
- Native listener (`GRPC_NATIVE_ADDR`): `grpc.StaticStreamWindowSize(64 KiB)`. BDP estimation grew each stream's window from network speed, not commit speed. A heap profile under NFR-3 showed 161 MB in `readDataFrame` buffers, with a peak RSS of 370–379 MB (FAIL). 64 KiB covers every netem profile's bandwidth-delay product (good-4g ≈ 62 KB, the others ≤ 30 KB), and grpc-go still widens the window for a message being read.
- `httpx.Listen`: `HTTP2.MaxReceiveBufferPerStream = 256 KiB` (net/http default 1 MiB). A client sending faster than its handler reads fills this buffer. With 200 in-progress gRPC uploads that was most of the remaining live heap (NFR-3 peaks of 327–341 MB). It applies to tus too: rest re-measured at 200.2 MB / 131 MB/s (NFR-2) and 207.8 MB (NFR-3), still PASS.
- Per-chunk staging info: **dropped** (explicit deviation from FR-6's literal "update committed offset (staging info + DB)"). FR-7 makes the DB offset authoritative: on every stream open the `.bin` is truncated to it, and nothing read the info file's `committed_offset`. The per-chunk `SaveInfo` cost a temp file, two fsyncs, a rename and a directory fsync per chunk. `{id}.json` is now written once at Init (`committed_offset` 0). The `.bin` is still fsynced and `UpdateCommitted` still runs before every ack (NFR-1). This is in the README contract deviations.
- NFR-3 commit rate after the fix: about 320 chunks/s on the dev Mac (200 x 252 4 KiB chunks in ~160 s), up from ~70/s. The load offers 1,280/s, so the held uploads finish in ~2m40s instead of 30 s. The test's criteria still pass: fresh 1 MiB upload ~10 s < 30 s, `/healthz` ≤ 51 ms, RSS < 300 MB, all uploads complete. The remaining cost is one `F_FULLFSYNC` plus one DB round trip through the podman port-forwarder per chunk. It was not re-measured with the server on Linux.
- Load test: `LOAD_PROTOCOL=grpc-native` dials the native listener (the load server now binds `GRPC_NATIVE_ADDR`); the DB row and metric label stay `grpc`.

## Decisions (grpc review fixes)

- Finalize deadline: `Service.finalize` itself now runs the finalizer under `context.WithTimeout(context.WithoutCancel(ctx), finalizeTimeout)`, so the stream, Init and Status retries all get it (Init/Status were previously cancelled with the request; a client that goes away no longer aborts a finalize mid-way on any path). The stream no longer wraps its context itself.
- `finalizeTimeout` (10 min) is duplicated in `grpcapi` instead of shared with `tusapi`: tusapi's constant is unexported, grpcapi must not import tusapi, and the only common neighbour is `finalize`, which grpcapi deliberately does not import ("Decisions (grpc service)"). The comment names tusapi as the source of the value.
- Per-chunk `UpdateCommitted` runs under `commitTimeout = 30 s` (still detached from the client). 30 s is a quarter of the 120 s idle timeout: long enough for a slow pool acquire or a DB failover blip, short enough that a hung DB ends the stream with `INTERNAL` (transient for the client) and releases the upload. The bytes are fsynced before the call, so a timed-out commit only means the next stream re-sends that chunk.
- Cancel re-checks the row with `lookup` after acquiring the upload: a row that is no longer `uploading` (completed by a stream that held it between the lookup and the acquire, or expired by the cleaner) is `NOT_FOUND`, as for a Cancel that sees it first, and its staging is left alone. `MarkCancelled` → `ErrNotFound` is also `NOT_FOUND` instead of `INTERNAL`. The test fake's `MarkCancelled` now returns `ErrNotFound` for a non-`uploading` row, like `grpcadapt`.
- Native listener: `grpc.MaxConcurrentStreams(100)` and `grpc.MaxHeaderListSize(16 KiB)` in `NewServer` (grpc-go defaults: unlimited, 16 MiB). The uploader and the load test use one connection per upload (one stream at a time), so only a client multiplexing more than 100 uploads on one connection queues. They have no effect on `/grpc` on the TLS listener (`ServeHTTP`), where net/http's HTTP/2 server applies its own defaults (250 streams, 1 MiB `MaxHeaderBytes`); left unchanged there. An oversized header list is rejected before the handler (`INTERNAL` on the grpc-go client, which checks the server's advertised limit before sending). README known limitations mention both limits.

## Decisions (acceptance refresh, lead)

- The very-poor smoke showed gRPC with 256 KiB chunks at 2.6–5.75× overhead, caused by the client's per-request timeout (60 s per 256 KiB) and gRPC keepalive (`Time 30s, Timeout 10s`). Both values are what the contract prescribes (§5.2 client HTTP settings, §5.4 dial options), and tus PATCH uses the same per-request timeout. The contract wins, so the uploader keeps them and the experiment measures the protocols as a contract client would run them. The difference that remains is protocol-inherent: tus keeps the partial bytes of a timed-out PATCH, while gRPC discards an unacked partial chunk.
- CSV `result=duplicate` can be the client's own upload: the server finalized it, the final `Ack{complete}` was lost, and the retried `Init` got `ALREADY_EXISTS`. Per contract §5.4 the client marks it done, and `cmd/summarize` counts `duplicate` as success. Left as is; read `duplicate` as "done, server already had it".

## Decisions (vps)

Single-VPS test/experiment deployment (`deploy/vps`, `mk/vps.mk`, README "Deploy to a VPS"). Choices given: one VPS (Ubuntu 24.04, Docker Engine + compose plugin; Debian 12 also works), IP only with self-signed TLS, MinIO and Postgres on the same VPS.

- **ES256 only, no DEV_MODE.** The experiment and e2e tooling (`cmd/devtoken`, uploader, netem harness) already work with ES256 (`devtoken -key`), so HS256 is not needed. `make vps-token` signs on the operator machine with `deploy/vps/secrets/jwt.key`; the VPS only gets `jwt.pub`, so a compromised VPS cannot mint tokens.
- **Own CA instead of a bare self-signed server cert** (unlike `make devcert`). Clients pin `ca.crt`, and the server cert (397 days, SAN = VPS IP + optional `--san`) can be re-signed for a new IP with `--renew-cert` without redistributing anything. The CA is P-256, 10 years, `pathlen:0`; the leaf has `CA:FALSE`, `digitalSignature`, `serverAuth`. The key and JWT recipe is the same openssl P-256 recipe as `make devcert`. `ca.key` and `jwt.key` never leave the operator machine.
- **Image built on the operator machine, no registry.** `deploy.sh` cross-compiles `cmd/server` (`CGO_ENABLED=0 -trimpath -ldflags="-s -w"`, `GOARCH=$VPS_ARCH`) and builds `deploy/vps/Dockerfile.prebuilt`, a copy of the root Dockerfile's final stage, with `--platform linux/$VPS_ARCH`. This is the same approach as the acceptance runs and avoids the in-VM compile that gets OOM-killed. No `RUN` step, so no emulation is needed for amd64 on an arm64 Mac. `docker save | gzip | ssh docker load` moves the image. Each deploy is tagged `vps-<commit>[-dirty]-<utc time>` and retagged `:vps` (what compose uses), and the three newest are kept for rollback.
- **Ports.** The container listens on `:443` itself (`sysctls: net.ipv4.ip_unprivileged_port_start=0`, Docker's default on bridge networks, explicit for other runtimes), so `Alt-Svc` advertises `:443`. Published: 443/tcp, 443/udp, 9090/tcp on `0.0.0.0` (IPv4). Admin 9100 and the MinIO console 9001 are on `127.0.0.1` (`make vps-tunnel`). Postgres and MinIO S3 are not published. Docker's published ports bypass ufw, so the compose file, not ufw, is what keeps them private; ufw covers everything else on the host.
- **MinIO credentials.** The server does not use the MinIO root user. `minio-init` creates a bucket-scoped policy `upload-server` (bucket list/location/multipart listing, object get/put/delete, multipart abort/list parts) and a user `S3_ACCESS_KEY` with it on every `up` (idempotent: `mc admin user add` updates the secret, and re-attaching succeeds with this mc release). The image has no `grep`, so the init script does not parse `mc` output. All secrets are hex from `openssl rand`, so they are safe inside `DATABASE_URL` without escaping.
- **Bind mounts under `/srv/sensor-upload`** (`pgdata` uid 70 mode 700, `minio` root 755, `staging` 65532 mode 750, `certs` `DEPLOY_USER:65532` mode 2750), created by `bootstrap.sh`. Disk use shows up in `df`/`du` and survives `docker compose down -v`. `certs/` is setgid so rsynced files (no `-p/-g`, `--chmod=F640`) get group 65532 and only the server container can read `server.key`. `deploy.sh` refuses to deploy if `certs/` does not have group 65532. `minio` is 755 because the server mounts it read-only as `DISK_PATH`.
- **Retention / disk pressure.** `RETENTION_MAX_AGE`, `DISK_PATH`, `DISK_HIGH_WATERMARK`, `DISK_LOW_WATERMARK` and `DISK_CHECK_INTERVAL` were added by another workstream at the same time, with the defaults given (168h, 85, 70, 1m). The compose file passes them with those defaults. `DISK_PATH=/data/disk` is `/srv/sensor-upload/minio` mounted read-only, so the watermarks track the filesystem holding the objects (on a single-disk VPS also staging and Postgres). Until that change is merged the server ignores the variables (unknown env vars are not an error).
- **Health.** The server image is distroless (no shell or curl), so it has no compose healthcheck. `deploy.sh` waits for `http://127.0.0.1:9100/readyz` over ssh (`READY_TIMEOUT`, 180 s) and then probes `https://<ip>/rest/files/` from the operator machine with `ca.crt` (401 without a token = TLS + firewall ok). On a failed wait it prints `compose ps` and the last 50 server log lines. Postgres and MinIO have healthchecks and the server waits for them (`service_healthy`, `minio-init` `service_completed_successfully`).
- **Limits for a 2–4 GB VPS:** server 1 GB with `GOMEMLIMIT=800MiB` (load-test peaks ≤ 250 MB, plus headroom for HTTP/3 and gRPC bursts), MinIO 768 MB, Postgres 512 MB (`shared_buffers=128MB`, `max_connections=50`), minio-init 256 MB, plus pids limits. Local boot measured idle at about 11 / 213 / 25 MB (server / MinIO / Postgres). Log rotation: json-file 10 MB × 5 per container. `stop_grace_period: 40s` covers `SHUTDOWN_TIMEOUT=30s`.
- **QUIC buffers.** `bootstrap.sh` writes `/etc/sysctl.d/60-sensor-upload-quic.conf` with `net.core.rmem_max`/`wmem_max = 7500000` (quic-go's recommendation; without it quic-go logs a buffer-size warning and HTTP/3 throughput suffers). These sysctls are not per network namespace, so the host value applies to the container. `VPS_QUIC_SYSCTL=0` skips it.
- **`gen-secrets.sh` idempotency.** Existing files are kept. If the existing server cert does not contain `--ip` (or does not match the full `--san` list), the script warns and suggests `--renew-cert`. `--force` regenerates everything and is documented as needing `make vps-wipe`, because Postgres bakes its password into pgdata at init.
- **`vps-wipe`** asks the operator to type the host, runs `compose down`, then deletes the contents of `pgdata/ minio/ staging/` from a throwaway `postgres:16-alpine` container. The image is already on the VPS, and this works for root and docker-group users even though the files belong to container uids. The directories and their ownership stay.
- Verification without a real VPS: shellcheck 0.11 clean, `docker compose config` (Compose 5.6) valid with `.env.example`, generated SAN checked with `openssl x509 -ext subjectAltName` and `openssl verify`, amd64 and arm64 cross-builds plus `--platform linux/amd64` image build (33 MB). The VPS compose file also booted unchanged on rootless podman, with a scratch override for SELinux labels only and other host ports. `/readyz` was ok, and all four protocols uploaded with an ES256 token from `make vps-token` and `-ca ca.crt` (HTTP/3 through the published UDP port). The minio-init first-boot path was re-checked on empty data: the first version's "already attached?" check matched the user name and skipped the attach, giving objstore `fail`. It was then torn down. `bootstrap.sh` and the ssh/rsync steps of `deploy.sh` could not be run.

## Decisions (verify endpoint, remote e2e)

- **`GET /files/sha256/{sha256}`, no authentication** (the user's explicit choice). The route lives outside `/rest/files/`, `/rest-http3/` and `/grpc/`, so it cannot collide with tus IDs or gRPC paths. The router mounts it as a plain mux prefix (`httpx.PrefixFiles`), and the gRPC dispatch only takes `/grpc/` paths, so a gRPC content type on `/files/…` still reaches the lookup. The handler (`internal/fileapi`) has its own `GET /files/sha256/{sha256}` mux pattern: HEAD is also answered, other methods get 405 and deeper paths 404.
- **Also on HTTP/3.** It took one `h3mux.Handle` line with the same handler, so sensors on `/rest-http3` can check without opening a TCP connection.
- **What it discloses.** It reports whether a completed upload with that sha256 exists, plus `size` and `completed_at` (UTC, RFC 3339). It never returns device_id, filename, object key, metadata or in-progress state, so uploading, failed, cancelled and expired rows are all `404 not_found`. Tradeoff: without a token, anyone who has a file (or guesses its hash) can confirm it was uploaded, and roughly when. The hash is 256 bits of the content, so it cannot be enumerated, but a known file can be confirmed. README security notes and known limitations say so. A device-scoped variant would need auth and would reveal less.
- Query: the existing `db.Repo.FindCompletedBySHA`, served by the partial unique index `uploads_sha256_completed`. No new SQL. The handler maps only `db.ErrNotFound` to 404; other errors give a generic `500 {"error":"internal error"}` and the cause is logged at error level, not sent (it can name hosts). A 5 s query timeout applies.
- Validation runs before the DB: exactly 64 lowercase hex characters, the same rule the upload metadata uses. Uppercase is 400, not normalized, so a client sees the same canonical form it must upload with. The log line records only the length of an invalid value, never the raw input.
- Headers: `Cache-Control: no-store` on every answer (a later upload changes the answer), `Content-Type: application/json`, `X-Content-Type-Options: nosniff`.
- Observability: `file_lookups_total{result="found|not_found|invalid|error"}` in `obs.Metrics`, and one info `file lookup` log line per request (error level on 500) with `method, proto, result, status, duration_ms, sha256`. This matches the per-request `tus request` line.
- **No rate limit.** Nothing reusable exists (no limiter in the codebase, `golang.org/x/time` is not a dependency). Each lookup is one indexed query, so this is recorded as future work, with a reverse proxy or firewall as the stopgap.
- **No uploader `-verify` mode.** `cmd/uploader` requires `-file`/`-dir` and an outbox. The README documents `curl --cacert certs/server.crt https://host:port/files/sha256/<hex>` instead.
- **Remote suite (`test/remote`, tag `remote`).** Every file is `_test.go` with the tag, so `go build/vet/test ./...` (default and `integration`) ignore it. There is no `TestMain`: `remoteEnv` loads the configuration once and skips each test when `REMOTE_URL` is unset, which keeps `go test -list` (`make e2e-remote-list`) working without configuration. `make lint` vets and staticchecks the tag (cheap: one package).
- Tokens: mint from `REMOTE_HMAC_SECRET` (HS256) or `REMOTE_JWT_KEY` (ES256 private key), or pass a fixed `REMOTE_TOKEN`. Minting covers short dev runs and gives the cross-device test a second device (`<device>-other`). A fixed token suits a production-like server where the tester only holds a token. Its device defaults to the token's unverified `device_id` claim. `REMOTE_OTHER_TOKEN` is optional, and without it only the cross-device subtest skips.
- Health: `/healthz` lives on the plain-HTTP admin listener, which a VPS usually does not expose. `TestRemoteHealth` therefore always checks the public listener (TLS handshake plus a lookup that must be 404) and adds `/healthz` and `/readyz` only with `REMOTE_ADMIN_URL`.
- Scenarios use `internal/client` (the contract client with outbox and backoff) for the happy-path upload per protocol and for duplicate → `result=duplicate`. They use raw tus and raw gRPC wherever exact codes or offsets are asserted: resume, 461, 401, 403/404, 400. Native-listener raw gRPC calls use bare method paths (deviation 12), and `/grpc` calls use `grpcprefix.DialOptions`.
- Duplicates are asserted as **461** / `ALREADY_EXISTS` (contract §2/§4). 460 is the checksum mismatch, which the suite does not provoke remotely because it would need a crafted wrong sha.
- Resume (tus): a PATCH whose body is cut off after ~1 chunk, then HEAD on a new connection must return an offset in `[64 KiB, size)`, and the upload finishes from it (`sendFrom` re-HEADs on 409). With tusd's lock handover the interrupted request ends with 400 and its bytes are kept, so the observed offset was 128 KiB. Resume (gRPC): a lock-step stream (one chunk per ack, so the server needs `GRPC_ACK_EVERY_N=1`) is abandoned after 2 acks. The second `Init` must return the same `upload_id` and the last acked offset, and `Status` must agree.
- Reruns: every test uses fresh random content, and unfinished uploads are cleaned up when the test ends (tus `DELETE`, gRPC `Cancel`), so a VPS run does not leave staging behind until `INCOMPLETE_TTL`.
- `make e2e-remote RUN=X` anchors the regexp as `^(X)$`. Plain `-run TestRemoteUploadREST` would also run `TestRemoteUploadRESTHTTP3`, and `RUN='A|B'` and `RUN='TestRemoteUpload.*'` still work.
- Proof run: the suite ran against this branch's `cmd/server` binary on the host (IP-only self-signed certificate `subjectAltName=IP:127.0.0.1`, throwaway Postgres container, local object store, HS256, native listener, admin listener). All 14 tests passed in 3.4 s. A second run with a fixed `REMOTE_TOKEN` and no native or admin URL passed and skipped as designed. The compose stack was not used: it runs an older image without the endpoint, and an experiment is using it.
## Decisions (retention)

Requirement (user): "wipe regularly for 7 days age. also wipe if disk near limit (ex: 70%-85%)". This is a test server, so finished files must not pile up.

- Scope: only `completed` uploads, which are the only ones with an object. In-progress rows belong to expiry (`INCOMPLETE_TTL`). Failed, cancelled and expired rows have no object and stay; they are small.
- Rows are **deleted**, not moved to a new terminal status. Deleting breaks no invariant. A tus HEAD/PATCH or gRPC `Status` for the old ref answers 404 / `NOT_FOUND` ("upload gone, start again"), as for any unknown ref. The partial unique index `uploads_sha256_completed` no longer holds the sha256, so the same file can be uploaded again. The orphan sweep already treats a missing row as terminal, and completed uploads have no staging anyway. A `purged` status would need a CHECK-constraint migration and a new case in every status switch, and the table would still grow, only to keep history nobody reads: the experiment results come from client CSVs, not the DB.
- Order and crash safety: `db.Repo.DeleteCompleted(id, deleteObject)` runs `DELETE … WHERE id = $1 AND status = 'completed' RETURNING storage_key` in a transaction, calls `deleteObject(storage_key)` (`objstore.Store.Delete`, where a missing object is success), and commits only if that succeeded. A crash or failure anywhere before the commit leaves the row `completed` (the object may already be gone), and the next pass deletes the missing object again and then the row. The reverse order (row first, then object) could leak an object forever after a crash. Worse, a new upload of the same file could complete in between: `Put` is idempotent, so it would skip writing because the key exists, and then lose the object.
- Dedup race: without care, a new upload of the same file whose finalizer checks `FindCompletedBySHA` while retention is deleting the old row would be told "duplicate" (`461` / `ALREADY_EXISTS`, and the client treats it as done) for a file that then disappears. `FindCompletedBySHA` now ends with `FOR SHARE`. That row lock conflicts with the uncommitted `DELETE`, so the lookup waits for the retention transaction and then finds no row (READ COMMITTED skips a row deleted by the transaction it waited on). The upload is then stored and completed normally under the same key. It costs nothing when no delete is running, since completed rows are never updated and the lock lasts one statement. Test: `TestRepoFindCompletedWaitsForDelete`, which fails without `FOR SHARE`.
- The transaction is held open during one object delete (S3: one `DeleteObject` round trip), on one pool connection at a time. Acceptable.
- Queries: `ListCompleted(minAge, limit)` lists `completed` rows with `completed_at < now() - minAge` (database clock, like `ListStale`), ordered `completed_at, id`, with a limit. `minAge = 0` lists every completed row, oldest first, for disk pressure. Migration `0002` adds the partial index `uploads_completed_at ON uploads (completed_at) WHERE status = 'completed'`.
- Component: `cleanup.Retention` (separate from `Cleaner`, same package). It runs in its own goroutine started by `app.Run`. The disk check and the age pass run in that one goroutine and never overlap: the disk check at start and every `DISK_CHECK_INTERVAL` (default 1m), the age pass at start and every `CLEANUP_INTERVAL`. `RETENTION_MAX_AGE=0` disables the age pass. Disk pressure has no off switch; `DISK_HIGH_WATERMARK=100` with `DISK_LOW_WATERMARK=99` makes it act only on a completely full disk (the e2e and load harnesses set that, because the dev Mac disk was at 86% and those tests share one DB).
- Batches: `DefaultRetentionBatch = 500` rows per `ListCompleted`. The age pass loops over batches until one comes back short. A batch with any failure ends the pass (the failed rows stay for the next pass), so a persistent failure such as S3 down cannot spin on the same rows. A row deleted by someone else meanwhile (`ErrNotFound`) is skipped silently. Each batch logs one info line, `retention batch` with `reason, listed, deleted, failed` (age adds `max_age`; disk adds `used_ratio_before, used_ratio`). Each upload logs a debug line.
- Disk pressure: `used = (blocks − bfree) × bsize` and `ratio = used / (used + bavail × bsize)`, the same formula as df's `Use%` (blocks reserved for root count as neither used nor available). From `syscall.Statfs` (`statfs_unix.go`; `!unix` builds return an error). Usage is measured at each check and sets `disk_used_ratio`. At or above the high watermark, the oldest completed uploads are deleted one by one, re-measuring after each, until usage is below the low watermark. statfs is microseconds, and re-measuring after every delete avoids overshooting by up to a whole batch. Stop conditions:
  - nothing completed is left: a warning if usage is still at or above high;
  - a batch with a failure;
  - a whole batch that did not lower used bytes: warning "disk usage did not drop … is DISK_PATH the object store's disk?". This guards against wiping every completed upload when `DISK_PATH` is not where the objects live (for example `OBJSTORE=s3` on a remote bucket with the default `DISK_PATH=STAGING_DIR`, or a disk filled by in-progress staging). The next check continues. Concurrent uploads, or a store that frees space asynchronously, can trigger it spuriously; that only throttles the deletes to one batch per check.
- `DISK_PATH` default: `OBJSTORE_LOCAL_DIR` when `OBJSTORE=local`, else `STAGING_DIR`. With MinIO on the same host, mount the host's MinIO data directory into the server container (read-only is enough) and point `DISK_PATH` at it: statfs then reports the shared host disk that MinIO and staging fill. `NewRetention` stats `DISK_PATH` once at startup, so a missing mount fails `app.New` instead of logging errors every minute.
- Config validation: `RETENTION_MAX_AGE` ≥ 0, `DISK_CHECK_INTERVAL` > 0, both watermarks integers in 1..100, and low < high.
- Metrics: `uploads_retention_deleted_total{reason="age"|"disk"}` (one per upload whose object and row were deleted) and gauge `disk_used_ratio` (0..1, last measurement). The name prefix `uploads_` differs from the older `upload_*` metrics because the names were fixed by the deploy work.
- Tests: unit tests with fakes and an injected `StatFunc` (`internal/cleanup/retention_test.go`). Integration tests: `internal/db/retention_integration_test.go` (queries, transactional delete, re-upload, `FOR SHARE` wait) and `internal/cleanup/retention_integration_test.go`. The latter covers a gRPC upload purged by age and then uploaded and completed again, disk pressure over the local store with usage measured from the object directory, and S3 deletes against MinIO.
